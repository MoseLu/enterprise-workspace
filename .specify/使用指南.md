# SpecKit 规范驱动开发使用指南

## 一、引言

### 1.1 什么是规范驱动开发

规范驱动开发（Spec-Driven Development）是一种系统化的软件开发方法论，它从根本上改变了传统软件开发的工作模式。在过去的几十年里，代码一直是软件开发的核心，规范文档往往被视为辅助性的工作，最终在开发过程中被丢弃或忽视。规范驱动开发彻底改变了这一范式：规范本身成为可执行的，直接生成可工作的实现，而不仅仅是指导开发。

这种方法论的核心思想是「先定义做什么和为什么做，再考虑怎么做」。通过首先建立清晰、规范的需求定义，然后基于这些定义进行技术规划和实施，团队可以显著减少返工、提高代码质量、加速开发进度。规范驱动开发特别适合与 AI 编程助手协作，因为它为 AI 提供了明确、详细的上下文信息，使 AI 能够生成更准确、更符合需求的代码。

GitHub 的 SpecKit 工具包为规范驱动开发提供了完整的工具链支持，包括模板、脚本和工作流程指南。本指南将帮助你将 SpecKit 集成到你的企业工作空间项目中，建立一套规范、高效的开发流程。

### 1.2 为什么要使用规范驱动开发

采用规范驱动开发可以带来多方面的好处。首先，从需求质量角度来看，规范驱动开发要求在开发开始之前就必须明确需求，这迫使团队在项目早期就发现和解决需求中的模糊之处和矛盾之处，从而减少后期因需求变更导致的返工。清晰的需求文档也为团队提供了共同的参考基准，减少沟通中的误解。

其次，从开发效率角度来看，规范驱动开发建立了一个结构化的工作流程，每个阶段都有明确的输入、输出和检查点。这种结构化的方法使得项目进度更容易跟踪和管理，团队成员可以清楚地了解项目的当前状态和下一步需要做什么。同时，规范化的文档也使得新成员更容易上手项目，因为他们可以通过阅读规范文档快速了解项目背景和需求。

第三，从代码质量角度来看，规范驱动开发要求在编码之前进行详细的技术设计，这使得开发人员能够预先考虑架构设计、性能优化、安全性等因素，而不是在编码过程中边写边改。规范中的验收标准也为测试提供了明确的依据，确保开发的功能符合预期。

最后，从 AI 协作角度来看，规范驱动开发为 AI 编程助手提供了丰富的上下文信息。AI 可以基于详细的规范文档生成更准确、更符合需求的代码，而不是依赖于可能不完整或不准确的对话历史。这大大提高了 AI 辅助开发的效率和质量。

### 1.3 本指南的使用方法

本指南旨在为你的企业工作空间项目提供完整的 SpecKit 集成指导。建议按照以下方式使用本指南：如果你是首次接触规范驱动开发，建议从第一章开始完整阅读，以理解规范驱动开发的核心理念和方法论。如果你已经有一定的规范驱动开发经验，可以直接跳转到第三章查看快速开始指南，或者根据需要查阅特定章节。

在实践过程中，建议将本指南与项目的实际规范文档结合使用。当你需要创建新的功能规格或技术计划时，可以参考第四章的模板和示例。当你在使用过程中遇到问题时，可以查看第五章的常见问题解答。如果你想深入了解规范驱动开发的最佳实践，可以参考第六章的内容。

## 二、安装与配置

### 2.1 环境准备

在开始使用 SpecKit 之前，你需要确保开发环境已经安装了必要的工具。这些工具是 SpecKit 正常运行的基础，包括版本控制、运行时环境和包管理工具。请按照以下步骤检查和安装所需的工具。

首先，你需要安装 Git。Git 是版本控制系统，SpecKit 的许多功能都依赖于 Git 进行分支管理和版本控制。如果你还没有安装 Git，可以从官方网站下载安装包，或者使用包管理器进行安装。安装完成后，通过运行 `git --version` 命令验证安装是否成功。

其次，你需要安装 uv 包管理工具。uv 是一个用 Rust 编写的高性能 Python 包管理工具，比传统的 pip 更快、更可靠。SpecKit 使用 uv 进行包管理和工具安装。安装 uv 的方法非常简单，在 Linux 或 macOS 上，你可以运行以下命令：

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

在 Windows 上，你可以使用 winget 进行安装：

```bash
winget install astral-sh.uv
```

或者使用 pip：

```bash
pip install uv
```

安装完成后，通过运行 `uv --version` 验证安装。

第三，你需要安装 Python 3.11 或更高版本。SpecKit 的 CLI 工具使用 Python 开发，因此需要 Python 运行时环境。你可以从 Python 官方网站下载安装包，或者使用包管理器进行安装。安装完成后，通过运行 `python3 --version` 或 `python --version` 验证安装。

最后，你需要安装一个支持的 AI 编程助手。SpecKit 支持多种 AI 编程助手，包括 Claude Code、Codex CLI、Cursor 和 Windsurf。这些工具提供了 `/speckit.*` 系列命令，用于执行规范驱动开发的各个阶段。你可以根据自己的偏好选择和安装其中一个或多个工具。安装完成后，确保这些工具可以在命令行中正常调用。

### 2.2 安装 Specify CLI

Specify CLI 是 SpecKit 的核心命令行工具，用于初始化项目、检查系统要求和运行各种开发任务。安装 Specify CLI 非常简单，推荐使用持久化安装方式，这样你可以在任何位置直接使用 `specify` 命令。

执行以下命令进行持久化安装：

```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
```

安装完成后，你可以通过运行 `specify --version` 来验证安装是否成功。如果命令返回版本号，说明安装成功。如果出现命令未找到的错误，可能需要重新加载终端配置文件或重启终端。

如果你只是临时使用 Specify CLI，也可以选择一次性运行方式，而不必进行持久化安装：

```bash
uvx --from git+https://github.com/github/spec-kit.git specify --help
```

这种方式的优点是不需要安装，缺点是每次运行都需要从网络下载工具，速度较慢。

要升级 Specify CLI 到最新版本，运行以下命令：

```bash
uv tool install specify-cli --force --from git+https://github.com/github/spec-kit.git
```

`--force` 参数确保即使已经安装也会重新安装最新版本。

### 2.3 系统检查与配置

在开始开发之前，建议先运行系统检查，确保所有必要工具都已正确安装。Specify CLI 提供了 `check` 命令，可以自动检查系统中是否安装了所需的各种工具：

```bash
specify check
```

这个命令会检查 Git、Python、uv 以及你指定使用的 AI 编程助手是否已安装。如果某个工具未安装，命令会给出相应的提示和建议。

如果你的开发环境需要使用代理服务器访问网络，或者需要在企业网络环境中使用，你可能需要配置相应的环境变量。例如，如果需要使用 GitHub Token 进行 API 请求，可以设置 `GH_TOKEN` 或 `GITHUB_TOKEN` 环境变量：

```bash
export GH_TOKEN="your-github-token"
```

或者在 PowerShell 中：

```powershell
$env:GH_TOKEN = "your-github-token"
```

在某些企业环境中，可能还需要配置 SSL/TLS 证书验证。如果遇到证书相关的问题，可以使用 `--skip-tls` 参数跳过验证（不推荐用于生产环境）。

### 2.4 项目初始化

你的企业工作空间项目已经预配置了 SpecKit 集成，因此通常不需要手动进行项目初始化。但如果你是从零开始初始化一个新项目，可以按照以下步骤进行。

首先，进入项目目录并初始化 SpecKit：

```bash
cd your-project-directory
specify init . --ai claude
```

`--ai` 参数指定你使用的 AI 编程助手，可选值包括 `claude`、`codex`、`cursor`、`windsurf` 等。Specify CLI 会在当前目录创建 `.specify` 目录，其中包含模板、脚本和配置文件。

如果你想在初始化时指定其他选项，可以使用以下参数：

- `--script ps`：使用 PowerShell 脚本（Windows 环境）
- `--no-git`：跳过 Git 仓库初始化
- `--ignore-agent-tools`：跳过 AI 代理工具检查
- `--force`：强制覆盖已存在的文件

初始化完成后，项目根目录会生成 `CLAUDE.md` 文件，这个文件为 AI 编程助手提供了项目指导信息。同时，`.specify` 目录中会创建完整的目录结构和模板文件。

## 三、快速开始

### 3.1 第一个功能开发流程

让我们通过一个完整的示例来了解规范驱动开发的整体流程。假设我们要开发一个「用户反馈管理」功能，包含提交反馈、查看反馈列表和处理反馈三个主要用户故事。

第一步是启动 AI 编程助手并创建功能规格。在项目根目录启动 Claude Code，然后运行 `/speckit.specify` 命令来描述我们要开发的功能：

```
开发一个用户反馈管理功能。用户可以在系统中提交反馈，包括反馈标题、详细描述、问题类型（Bug/建议/咨询）和优先级（高/中/低）。管理员可以查看所有反馈列表，按状态（待处理/处理中/已完成）和问题类型进行筛选。管理员可以将反馈状态从待处理改为处理中或已完成，并在处理完成后填写处理说明。
```

AI 助手会根据你的描述生成详细的功能规格文档，保存为 `specs/FEATURE-XXXX-XXXX/spec.md`。这个文档包含用户故事、功能需求、非功能需求、数据模型、接口设计等内容。

第二步是澄清和完善规格。阅读生成的规格文档，如果有不清晰或不完整的地方，运行 `/speckit.clarify` 命令进行澄清。你可以这样问：

```
对于反馈处理流程，当管理员将状态改为已完成时，是否需要通知提交反馈的用户？如果需要，通过什么方式通知（站内消息/邮件）？
```

AI 助手会基于规格文档中的信息回答你的问题，或者指出哪些内容在当前规格中还没有定义，需要补充。

第三步是创建技术实施计划。规格完善后，运行 `/speckit.plan` 命令来创建技术实施计划：

```
基于以下技术栈创建用户反馈管理功能的技术实施计划：
- 前端：React 18 + TypeScript + Vite
- 后端：Go + Gin + GORM
- 数据库：PostgreSQL 14+
- 缓存：Redis 7+
- 使用 RESTful API 设计
```

AI 助手会生成详细的技术实施计划，保存为 `specs/FEATURE-XXXX-XXXX/plan.md`。这个文档包含技术栈选择、前后端架构设计、数据库设计、API 接口设计、性能优化策略等内容。

第四步是生成任务分解。技术计划确定后，运行 `/speckit.tasks` 命令将计划分解为具体的任务：

```
根据实施计划生成任务分解，包括前端、后端和数据库相关任务。任务应该按照用户故事组织，识别可以并行执行的任务。
```

AI 助手会生成任务列表，保存为 `specs/FEATURE-XXXX-XXXX/tasks.md`。每个任务都有详细的描述、验收标准、依赖关系和工时估算。

第五步是执行实施开发。任务分解完成后，运行 `/speckit.implement` 命令开始实际开发：

```
开始执行任务列表中的所有任务。遵循项目代码规范，编写单元测试，确保代码质量。
```

AI 助手会按照任务列表的顺序执行开发任务，每个任务完成后会更新任务状态。你可以随时查看 `tasks.md` 文件了解当前进度。

### 3.2 使用命令行脚本

除了使用 AI 编程助手的 `/speckit.*` 命令，你也可以使用 SpecKit 提供的命令行脚本来辅助开发。这些脚本提供了额外的功能和自动化能力。

创建新功能脚本可以帮助你快速初始化功能目录结构：

```bash
# 基本用法
bash .specify/scripts/create-new-feature.sh "用户反馈管理"

# 指定 AI Agent
bash .specify/scripts/create-new-feature.sh "用户反馈管理" --ai claude

# 强制覆盖已存在的目录
bash .specify/scripts/create-new-feature.sh "用户反馈管理" --force

# 不创建 Git 分支
bash .specify/scripts/create-new-feature.sh "用户反馈管理" --no-git
```

这个脚本会自动创建功能目录，复制相应的模板文件，并进行必要的初始化工作。

设置实施计划脚本可以帮助你准备技术实施阶段的工作：

```bash
# 指定功能编号
bash .specify/scripts/setup-plan.sh --feature FEATURE-20260201-0001

# 指定 AI Agent 并跳过技术调研
bash .specify/scripts/setup-plan.sh --feature FEATURE-20260201-0001 --ai claude --skip-research

# 显示详细输出
bash .specify/scripts/setup-plan.sh --feature FEATURE-20260201-0001 --verbose
```

这个脚本会检查前置条件，显示技术栈选项，获取用户的技术选择，执行技术调研，并生成各种辅助文档。

更新 CLAUDE.md 脚本可以根据当前项目状态更新项目的 `CLAUDE.md` 文件：

```bash
# 预览更改
bash .specify/scripts/update-claude-md.sh --dry-run

# 强制覆盖现有文件
bash .specify/scripts/update-claude-md.sh --force

# 显示完整的项目状态信息
bash .specify/scripts/update-claude-md.sh --all
```

这个脚本会检测项目中的产品列表、功能列表、Git 状态等信息，并生成更新的 `CLAUDE.md` 文件。

### 3.3 查看项目状态

在开发过程中，你可能需要随时了解项目的当前状态，包括有哪些功能正在开发中、每个功能的进度如何等。可以通过以下方式查看项目状态。

查看 Git 分支状态可以了解当前正在进行的开发工作：

```bash
git branch -a
git status
git log --oneline -10
```

查看功能目录可以了解已完成和正在进行的功能：

```bash
ls -la .specify/memory/
ls -la specs/
```

查看任务状态可以了解每个功能的开发进度：

```bash
cat specs/FEATURE-XXXX-XXXX/tasks.md
```

## 四、模板参考

### 4.1 功能规格模板

功能规格模板（`templates/spec-template.md`）为功能需求文档提供了标准化的结构。使用这个模板可以确保所有功能规格文档都包含必要的信息，便于团队成员理解和参考。

模板的主要章节包括：

**概述部分**要求填写功能名称、所属模块、优先级、目标用户、背景与动机等信息。优先级应该明确区分 P0（核心功能）、P1（重要功能）、P2（增强功能）和 P3（未来规划）。目标用户部分应该描述谁会使用这个功能，以及他们的角色和职责。

**用户故事部分**要求使用标准格式描述用户故事：作为[用户角色]，我希望[执行某个动作]，以便[获得某个价值]。每个用户故事应该有明确的验收标准和优先级。用户故事应该聚焦于用户目标，而不是具体的技术实现。

**功能需求部分**详细列出每个功能点，包括功能描述、前置条件、后置条件、交互流程、UI/UX 要求、业务规则和数据要求。每个功能应该有唯一的编号，便于跟踪和引用。

**非功能需求部分**涵盖性能、安全、兼容性、可用性和可维护性等方面的要求。性能需求应该包含具体的指标值和测量方法。安全需求应该明确认证、授权、数据加密和审计日志等方面的要求。

**数据模型部分**定义功能涉及的数据实体、字段、类型和约束。应该包含实体关系图或说明，以及数据流转描述。

**接口设计部分**详细定义每个 API 的路径、方法、请求参数、响应参数和错误码。API 设计应该符合 RESTful 最佳实践，使用标准的 HTTP 方法和状态码。

### 4.2 技术实施计划模板

技术实施计划模板（`templates/plan-template.md`）为技术设计文档提供了完整的结构。这个模板涵盖了从系统架构到部署运维的各个方面，确保技术方案全面且可实施。

模板的主要章节包括：

**项目概述部分**总结功能需求，列出技术栈选择，说明架构设计思路。技术栈选择应该包含每个技术选型的版本要求和选型理由，便于后续评审和决策。

**详细设计部分**是模板的核心，包含前端设计、后端设计、数据库设计、缓存设计和消息队列设计。前端设计应该包含目录结构、组件设计、状态管理和 API 服务层设计。后端设计应该包含目录结构、数据模型、服务层和 API 处理器设计。数据库设计应该包含表结构、索引和关联关系。缓存设计应该包含缓存策略和更新策略。消息队列设计应该包含消息定义和消费者设计。

**API 设计部分**详细列出所有 API 接口，包括路径、方法、请求和响应格式。应该使用 JSON Schema 或类似方式定义数据结构，使用标准的 HTTP 状态码表示操作结果。

**安全设计部分**描述认证授权方案、数据安全措施和接口安全措施。安全设计应该符合项目的安全原则和合规要求。

**性能设计部分**列出性能指标目标，优化策略和监控方案。性能设计应该考虑高并发场景和大数据量场景。

**部署设计部分**描述部署架构、环境配置和回滚策略。部署设计应该支持蓝绿部署或金丝雀发布等高级部署策略。

### 4.3 任务分解模板

任务分解模板（`templates/tasks-template.md`）为任务列表提供了标准化的格式。这个模板确保任务分解足够细粒度，便于跟踪和管理。

模板的主要部分包括：

**任务概览部分**列出所有任务的统计信息，包括总任务数、前端任务数、后端任务数、基础设施任务数和预计工期。应该包含任务依赖关系的可视化图示。

**阶段划分部分**按照用户故事或功能模块将任务划分为多个阶段。每个阶段应该有明确的目标和验收标准。阶段之间应该有清晰的依赖关系。

**任务详情部分**描述每个任务的具体内容，包括任务描述、验收标准、涉及文件、依赖关系、工时估算和检查点。任务描述应该足够详细，以便开发人员可以直接开始工作。验收标准应该是可测试的，便于验证任务是否完成。

**执行记录部分**用于跟踪任务的实际执行情况，包括状态、负责人、开始时间和完成时间。问题追踪部分用于记录开发过程中发现的问题和处理情况。

**验收总结部分**用于记录功能验收的最终结果，包括功能验收、非功能验收和流程验收。遗留问题部分记录无法在本次开发中解决的问题和后续处理计划。

## 五、常见问题

### 5.1 安装与配置问题

在安装和配置 SpecKit 的过程中，开发者可能会遇到各种问题。本节总结了最常见的问题及其解决方案，帮助你快速解决安装过程中的困难。

如果 `specify` 命令未找到，首先检查 uv 工具是否正确安装。运行 `uv --version` 验证安装。如果 uv 已安装但 `specify` 命令不可用，可能需要重新加载终端配置文件。在 bash 中运行 `source ~/.bashrc` 或 `source ~/.bash_profile`，在 zsh 中运行 `source ~/.zshrc`。如果问题仍然存在，可以尝试重新安装 Specify CLI，并添加 `--force` 参数。

如果遇到 SSL 证书相关错误，可能是因为网络代理或防火墙配置导致的。在企业网络环境中，可能需要配置相应的代理设置或导入企业证书。如果需要临时跳过 SSL 验证，可以使用 `--skip-tls` 参数（仅用于调试，不推荐用于生产环境）。

如果 AI 编程助手命令不可用，确保你已在系统中正确安装并配置了相应的工具。检查 `PATH` 环境变量，确保 AI 工具的可执行文件所在目录已包含在 PATH 中。对于 Claude Code，可能需要登录账户并完成认证流程。

### 5.2 使用过程中的问题

在使用 SpecKit 进行开发的过程中，开发者可能会遇到一些操作层面的问题。本节提供了这些问题的解决方案。

如果 AI 生成的规格或计划不符合预期，首先检查你的提示词是否足够具体和详细。AI 的输出质量很大程度上取决于输入的质量。尝试将复杂的需求分解为多个简单的部分，逐步让 AI 处理。如果仍然不理想，可以使用 `/speckit.clarify` 命令让 AI 澄清规格中的模糊之处，然后基于澄清后的结果重新生成。

如果任务分解粒度不适当，可以通过编辑 `tasks.md` 文件手动调整任务划分。将太大的任务拆分为更小的子任务，或者将太琐碎的任务合并为中等粒度的任务。调整后可以继续使用 `/speckit.implement` 命令，AI 会从上次停止的地方继续执行。

如果需要跳过某个任务直接执行后面的任务，可以在 `tasks.md` 中将跳过任务的验收标准标记为「不适用」，然后运行 `/speckit.implement`。AI 会按照任务列表的顺序执行，但会跳过那些标记为不适用或已满足条件的任务。

如果 AI 生成的代码不符合项目规范，可以先让 AI 阅读项目的 `constitution.md` 和 `CLAUDE.md` 文件，了解项目的编码标准和最佳实践。然后重新生成代码，或者手动调整 AI 生成的代码以符合规范。

### 5.3 与现有流程整合的问题

将 SpecKit 整合到现有开发流程中可能会遇到一些挑战。本节提供了整合过程中常见问题的解决方案。

如果你的团队已经有一套需求管理流程，可以在 SpecKit 的规格文档与现有需求文档之间建立链接关系。在 `spec.md` 中引用现有需求文档的编号或链接，确保不同文档之间的一致性。

如果你的团队使用不同的分支策略，可以根据实际情况调整 SpecKit 的分支命名规则。修改 `create-new-feature.sh` 脚本中的分支名称生成逻辑，使其符合你的团队规范。

如果你的团队使用不同的项目管理工具（如 Jira、Trello 等），可以将 SpecKit 生成的任务列表导入到这些工具中。任务列表中的信息（编号、名称、描述、验收标准等）可以方便地转换为这些工具中的任务格式。

## 六、最佳实践

### 6.1 需求定义最佳实践

需求定义是规范驱动开发的起点，高质量的需求定义可以大大提高后续阶段的效率和质量。以下是需求定义阶段的一些最佳实践。

首先，专注于用户目标而不是技术实现。需求文档应该描述用户想要达到什么目标，以及为什么这个目标对他们很重要，而不是描述如何实现这个目标。例如，「用户希望能够快速找到他们需要的文档」比「在搜索框中输入关键词并显示匹配结果」是更好的需求描述。

其次，使用标准化的用户故事格式。每个用户故事应该遵循「作为[角色]，我希望[功能]，以便[价值]」的格式。用户故事应该有明确的验收标准，这些标准应该是具体的、可测试的。例如，「当用户在搜索框中输入至少三个字符时，系统应在 200 毫秒内显示搜索建议」是一个好的验收标准。

第三，优先考虑最小可行产品。在定义功能范围时，先识别核心功能，然后再考虑增强功能。将功能按照优先级分为 P0（必须实现）、P1（应该实现）和 P2（可以实现）三个级别。优先完成 P0 功能，确保核心价值能够快速交付。

第四，识别并记录假设和不确定性。在需求定义过程中，如果存在某些假设或不确定性，应该明确记录下来。这些假设和不确定性应该在后续的澄清阶段得到确认或解决。

第五，保持需求文档的可追溯性。为每个需求分配唯一的编号，并建立需求与其他文档（设计文档、测试用例等）之间的追溯关系。这有助于管理需求变更，并确保所有相关文档同步更新。

### 6.2 技术设计最佳实践

技术设计阶段需要将需求转化为具体的技术方案。以下是技术设计阶段的一些最佳实践。

首先，进行技术选型评估。在选择技术栈时，不仅要考虑技术本身的能力，还要考虑团队的技术能力、社区支持、长期维护成本等因素。避免选择过于新或过于小众的技术，以降低维护风险。

其次，遵循已建立的项目原则。项目的 `constitution.md` 文件定义了代码质量、用户体验、安全性等方面的原则。技术设计应该严格遵循这些原则，确保所有设计决策都符合项目的要求。

第三，设计可扩展的架构。在设计系统架构时，要考虑未来的扩展需求。使用模块化的设计，使得各个组件可以独立开发和部署。接口设计应该保持稳定，避免频繁变更影响依赖方。

第四，重视安全性设计。在技术设计阶段就要考虑安全性，包括认证授权、数据加密、输入验证、审计日志等方面。安全性不应该被视为后期添加的功能，而应该是设计的一部分。

第五，编写清晰的设计文档。设计文档应该清晰、准确、完整，使团队成员能够基于文档进行实现。关键的设计决策应该说明选择理由，便于后续评审和优化。

### 6.3 开发实施最佳实践

开发实施阶段是将设计转化为可工作代码的过程。以下是开发实施阶段的一些最佳实践。

首先，遵循编码规范。项目已经建立了编码规范，包括代码风格、命名约定、注释要求等。在编写代码时，应该严格遵循这些规范，确保代码的一致性和可读性。

其次，编写测试用例。遵循测试驱动开发（TDD）或行为驱动开发（BDD）的方法论，在编写功能代码之前先编写测试用例。这有助于确保代码的可测试性，并提供安全的回归测试网。

第三，进行代码审查。所有代码在合并到主分支之前都应该经过代码审查。代码审查不仅关注代码的正确性，还要关注代码的可读性、可维护性和性能。审查者应该提供建设性的反馈，帮助改进代码质量。

第四，保持提交粒度适中。每次提交应该是一个完整的、可工作的变更。避免将多个不相关的更改混在同一个提交中。清晰的提交历史有助于追踪变更和回滚问题。

第五，及时更新文档。代码变更后，应该同步更新相关的设计文档、API 文档和用户文档。过时的文档比没有文档更有害，因为它会误导开发者。

### 6.4 团队协作最佳实践

规范驱动开发的一个重要优势是它可以促进团队协作。以下是团队协作方面的一些最佳实践。

首先，建立共享的术语表。项目中的术语应该保持一致，避免不同团队成员使用不同的术语描述同一个概念。在 `constitution.md` 或专门的术语表中定义关键术语，确保所有团队成员理解一致。

其次，定期进行同步会议。虽然规范驱动开发强调结构化的工作流程，但团队成员之间的定期沟通仍然很重要。建议每周进行一次短会，同步各自的进展、遇到的问题和需要的帮助。

第三，建立知识共享机制。团队成员在开发过程中积累的经验和教训应该被记录和分享。可以创建内部的知识库，记录常见问题的解决方案、最佳实践和踩坑经历。

第四，持续改进流程。规范驱动开发不是一成不变的流程，团队应该根据实际情况持续改进。定期回顾流程中的问题和改进机会，调整工作方法以适应团队的需求。

第五，尊重个人工作风格。规范驱动开发提供了结构化的框架，但团队成员在工作风格上可以有一定的灵活性。鼓励团队成员在遵循规范的前提下，探索适合自己的高效工作方式。

### 8.2 术语表

以下是本指南中使用的主要术语：

**规范驱动开发（Spec-Driven Development）**：一种软件开发方法论，强调通过详细的规范文档来驱动开发流程，从需求定义到代码实现。

**SpecKit**：GitHub 开源的规范驱动开发工具包，提供模板、脚本和工作流程支持。

**功能规格（Specification）**：描述功能需求、用户故事、交互流程等内容的文档。

**实施计划（Plan）**：描述技术实现方案、架构设计、接口定义等内容的文档。

**任务分解（Task Breakdown）**：将实施计划分解为可执行任务的列表。

**用户故事（User Story）**：使用「作为[角色]，我希望[功能]，以便[价值]」格式描述的需求。

**Constitution**：项目的治理原则，定义了代码质量、安全性、用户体验等方面的标准。
