要确保多技术栈工作区目录架构在**开发（dev）、测试（test）、生产（prod）** 三环境的一致性，核心思路是 **「标准化目录结构+配置与代码分离+自动化流程固化+一致性校验」**，结合你现有的GitHub Actions/Jenkins流水线，以下是可落地的完整方案：

## 一、 目录结构一致性：强制标准化，禁止环境差异化修改
目录结构是一致性的基础，必须通过**版本控制+校验脚本** 强制所有环境使用完全相同的目录层级，不允许在任意环境手动增删/修改目录。

### 1. 核心规则：目录结构纳入Git强管控
- **所有环境共用同一套Git仓库**：开发、测试、生产环境的工作区目录结构，必须来自Git仓库的同一分支（如 `develop` 对应测试环境，`main` 对应生产环境），禁止在测试/生产环境手动调整目录（如新增文件夹、删除配置文件）。
- **目录结构模板化**：在根目录新增 `scripts/ci/check-structure.sh` 脚本，**校验目录完整性和规范性**，示例如下：
  ```bash
  #!/bin/bash
  # 检查必要目录是否存在
  REQUIRED_DIRS=(
    "frontend/apps" "frontend/packages"
    "backend/common" "backend/bootstrap"
    "auxiliary/python" "auxiliary/go"
    ".cicd/github-actions" ".cicd/jenkins"
    "infra/docker" "docs/architecture"
  )

  for dir in "${REQUIRED_DIRS[@]}"; do
    if [ ! -d "$dir" ]; then
      echo "ERROR: 目录 $dir 缺失，目录结构不符合规范！"
      exit 1
    fi
  done

  echo "目录结构校验通过！"
  exit 0
  ```
- **CI流水线强制触发校验**：在GitHub Actions的 `ci.yml` 和Jenkins的 `Jenkinsfile.ci` 中，**将目录校验作为前置步骤**，不通过则终止后续流程：
  ```yaml
  # GitHub Actions 示例片段
  jobs:
    check-structure:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - name: 校验目录结构一致性
          run: ./scripts/ci/check-structure.sh
  ```

### 2. 跨环境统一编辑器规范
在根目录放置 **`.editorconfig`** 和 **`.gitattributes`**，强制所有开发者/环境使用相同的文件格式和编码，避免因换行符、缩进差异导致的目录/文件识别问题：
```ini
# .editorconfig 示例
root = true

[*]
charset = utf-8
indent_style = space
indent_size = 2
end_of_line = lf
trim_trailing_whitespace = true
insert_final_newline = true

[*.sh]
end_of_line = lf

[*.yml]
indent_size = 2
```

## 二、 配置一致性：配置与代码分离，环境参数动态注入
环境差异的核心是**配置不同**，而非目录或代码不同。需通过 **「配置中心+环境变量+配置模板」** 实现配置隔离，同时保证配置加载逻辑一致。

### 1. 配置分层策略（三环境统一加载逻辑）
| 配置层级 | 作用 | 存储位置 | 环境差异化处理 |
|----------|------|----------|----------------|
| 全局通用配置 | 跨环境不变的参数（如API路径前缀、日志格式） | `frontend/packages/config/src/common.ts`、`backend/common/src/main/resources/common.properties` | 代码固化，无差异化 |
| 环境专属配置 | 环境差异化参数（如中间件地址、数据库账号） | 开发环境：`.env`；测试/生产：Nacos/CI密钥 | 通过环境变量 `ENV` 动态切换 |
| 敏感配置 | 密码、密钥等 | 开发环境：`.env`（加入.gitignore）；测试/生产：Jenkins Credentials/GitHub Secrets | 绝对不提交到Git，通过CI/CD注入 |

### 2. 统一配置加载流程（三环境相同）
所有技术栈遵循**「先读环境变量→再读配置中心→最后读本地模板」** 的加载逻辑，确保不同环境的配置读取规则一致：
- **前端**：在 `frontend/packages/config/src/index.ts` 中统一加载配置：
  ```typescript
  const ENV = process.env.ENV || "dev";
  // 加载对应环境的配置
  const envConfig = await import(`./${ENV}.ts`);
  // 合并通用配置和环境配置
  export const config = { ...commonConfig, ...envConfig };
  ```
- **后端**：通过SpringBoot的 `@Profile` 注解和Nacos配置中心实现环境切换，三环境的 `application.yml` 结构完全一致：
  ```yaml
  spring:
    profiles:
      active: ${ENV:dev} # 由环境变量 ENV 决定激活哪个配置
    cloud:
      nacos:
        config:
          server-addr: ${NACOS_ADDR} # 环境变量注入
  ```
- **辅助项目（Python/Go）**：通过读取环境变量加载配置，例如Python：
  ```python
  import os
  ENV = os.getenv("ENV", "dev")
  NACOS_ADDR = os.getenv("NACOS_ADDR")
  ```

### 3. 配置模板同步（三环境统一模板）
在 `.cicd/env` 目录下存放**配置模板**（`test.env.example`、`prod.env.example`），确保测试/生产环境的配置项与开发环境一致，避免出现“测试环境有某个配置，生产环境没有”的问题：
```
# .cicd/env/prod.env.example
ENV=prod
NACOS_ADDR=prod-nacos:8848
REDIS_ADDR=prod-redis:6379
KEYCLOAK_ADDR=prod-keycloak:8080
```

## 三、 构建一致性：统一构建脚本，镜像标准化
构建过程是环境一致性的关键环节，需保证**开发、测试、生产使用同一套构建脚本和镜像打包规则**，避免“开发能构建，生产构建失败”的问题。

### 1. 统一构建脚本，参数化环境差异
所有构建逻辑封装在根目录 `scripts/ci/` 下的脚本中，**脚本本身无环境差异化代码**，仅通过参数区分环境：
- 前端构建脚本 `scripts/ci/frontend-build.sh`：
  ```bash
  #!/bin/bash
  ENV=$1 # 接收环境参数（dev/test/prod）
  cd frontend
  pnpm install
  pnpm run build -- --env $ENV # 传递环境参数，无脚本差异化
  ```
- 后端构建脚本 `scripts/ci/backend-build.sh`：
  ```bash
  #!/bin/bash
  ENV=$1
  cd backend
  mvn clean package -DskipTests -P$ENV # 通过Maven Profile切换环境，脚本无差异
  ```

### 2. 镜像标准化：一次构建，多环境运行
采用 **「Docker多阶段构建」**，确保开发、测试、生产使用**同一个镜像**，仅挂载不同配置：
- 所有服务的Dockerfile放在 `infra/docker/` 下，三环境共用，例如前端Dockerfile：
  ```dockerfile
  # 多阶段构建：构建阶段
  FROM node:20-alpine as builder
  WORKDIR /app
  COPY frontend/ .
  RUN pnpm install && pnpm run build -- --env $ENV

  # 运行阶段
  FROM nginx:alpine
  COPY --from=builder /app/dist /usr/share/nginx/html
  COPY infra/docker/frontend/nginx.conf /etc/nginx/conf.d/default.conf
  # 运行时通过环境变量注入配置，镜像本身无差异化
  ```
- **镜像标签规则统一**：所有环境的镜像标签格式为 `[服务名]:[git-commit-id]-[env]`，例如 `frontend:abc123-prod`，确保镜像版本可追溯，且环境标识清晰。

## 四、 部署一致性：自动化流水线固化部署流程
通过GitHub Actions和Jenkins流水线，**固化部署步骤**，确保测试/生产环境的部署流程与开发环境的验证流程完全一致，避免手动部署的差异。

### 1. 流水线步骤统一（三环境相同的步骤模板）
不管是开发环境的本地验证，还是测试/生产的自动化部署，都遵循以下步骤，差异仅在于**触发条件和目标环境**：
```
代码提交 → 目录结构校验 → 依赖缓存 → 构建 → 单元测试 → 镜像打包 → 镜像推送 → 部署 → 健康检查 → 回滚（失败时）
```
- **开发环境**：本地执行 `scripts/dev/start-all.sh`，模拟流水线步骤，验证功能；
- **测试环境**：提交PR到 `develop` 分支，自动触发GitHub Actions/Jenkins流水线，执行上述步骤；
- **生产环境**：合并代码到 `main` 分支，手动触发流水线（需审批），执行**与测试环境完全相同**的步骤，仅替换部署目标地址。

### 2. 部署脚本统一，环境参数化
部署逻辑封装在 `scripts/cd/` 下的脚本中，通过参数指定部署环境，例如 `deploy.sh`：
```bash
#!/bin/bash
ENV=$1 # dev/test/prod
# 加载对应环境的配置
source .cicd/env/$ENV.env
# 部署逻辑（如k8s apply、docker-compose up）
kubectl apply -f infra/k8s/$ENV/ --namespace $ENV
# 健康检查
curl -f http://$SERVICE_ADDR/health || (echo "部署失败，执行回滚" && ./scripts/cd/rollback.sh $ENV && exit 1)
```

### 3. 回滚机制统一（三环境相同的回滚逻辑）
所有环境的回滚脚本 `scripts/cd/rollback.sh` 完全一致，回滚逻辑为：**恢复上一个版本的镜像+配置**，确保失败时的回滚操作无环境差异。

## 五、 一致性保障的核心原则总结
| 保障维度 | 核心措施 | 工具/脚本 |
|----------|----------|-----------|
| 目录结构 | Git强管控+CI校验 | `check-structure.sh` + 流水线前置步骤 |
| 配置 | 配置与代码分离+环境变量注入 | Nacos + `.env.example` + CI密钥 |
| 构建 | 统一构建脚本+Docker多阶段构建 | `frontend-build.sh` + `Dockerfile` |
| 部署 | 流水线固化步骤+参数化部署 | GitHub Actions/Jenkins + `deploy.sh` |

通过以上方案，可确保工作区目录架构在开发、测试、生产环境的**结构、配置加载逻辑、构建流程、部署步骤完全一致**，从根源上消除“环境不一致导致的问题”。
