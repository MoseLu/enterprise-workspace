# Enterprise Workspace 系统级开发规范

> **规范等级**：强制执行（Mandatory）
>
> **适用范围**：Enterprise Workspace Monorepo 所有项目
>
> **版本**：1.0.0
>
> **最后更新**：2026-02-01

## 一、规范概述

### 1.1 规范目的

本文档定义了 Enterprise Workspace Monorepo 的**系统级开发规范**，所有子项目必须强制遵循。这些规范是确保多项目协同开发一致性的基础，任何违反规范的操作都将被 CI/CD 流水线拒绝。

### 1.2 规范等级

| 等级 | 标识 | 说明 |
|------|------|------|
| **强制** | 🔴 [M] | 必须遵守，违反将导致 CI 失败 |
| 推荐 | 🟡 [R] | 建议遵守，提升代码质量 |
| 可选 | 🟢 [O] | 根据项目需要选择执行 |

### 1.3 适用范围

本文档适用于 Enterprise Workspace 下的所有项目：

```
E:\enterprise-workspace\
├── products/                    # 核心产品项目
│   ├── devstation/             # 必须遵循
│   ├── ops-platform/           # 必须遵循
│   ├── agent-orchestrator/     # 必须遵循
│   └── agent-cli-web/          # 必须遵循
├── services/                   # 后端服务
│   ├── backend/                # 必须遵循
│   └── rag/                    # 必须遵循
├── tools/                      # 工具项目
│   └── scheduler/              # 必须遵循
└── ...                         # 所有子项目
```

## 二、Git 分支策略规范

> 🔴 [M] **强制执行** - 所有项目必须严格遵循

### 2.1 分支模型

采用 **Git Flow** 分支模型，包含 5 种分支类型：

```
                    ┌─────────────────────────────────────────┐
                    │              长期分支                    │
                    ├─────────────────────────────────────────┤
                    │  🌟 main/release    生产环境（受保护）    │
                    │  🔧 develop         开发主干（受保护）    │
                    ├─────────────────────────────────────────┤
                    │              短期分支                    │
                    ├─────────────────────────────────────────┤
                    │  ✨ feature/*      新功能开发             │
                    │  🐛 bugfix/*       常规 bug 修复          │
                    │  🚨 hotfix/*       紧急热修复             │
                    └─────────────────────────────────────────┘
```

### 2.2 分支命名规范

| 分支类型 | 命名模式 | 示例 | 说明 |
|---------|---------|------|------|
| **主分支** | `main` | `main` | 生产环境代码，永远稳定 |
| **开发分支** | `develop` | `develop` | 开发主干，集成测试通过 |
| **功能分支** | `feature/<name>` | `feature/user-auth` | 新功能开发 |
| **修复分支** | `bugfix/<desc>` | `bugfix/login-error` | 非紧急 bug 修复 |
| **热修复分支** | `hotfix/<ver>` | `hotfix/v1.2.1` | 紧急生产环境修复 |

### 2.3 分支命名规则

#### 2.3.1 允许的字符

- 英文字母（a-z, A-Z）
- 数字（0-9）
- 连字符（-）
- 下划线（_）
- 斜杠（/）

#### 2.3.2 禁止的字符

- 空格
- 中文字符
- 特殊符号（!@#$%^&*()=+{}[]|\\:;\"'<>,?/）

#### 2.3.3 长度限制

- 分支名称总长度：不超过 100 字符
- 路径部分（feature/ 后）：不超过 50 字符

### 2.4 分支生命周期

#### 2.4.1 功能分支 (feature/*)

```
创建流程:
main/release ──→ develop ──→ feature/<name> ──→ develop ──→ main/release

操作步骤:
1. 从 develop 创建分支
   git checkout develop
   git checkout -b feature/new-feature

2. 开发并提交
   git add .
   git commit -m "feat(scope): add new feature"

3. 推送到远程
   git push -u origin feature/new-feature

4. 创建 PR 合并到 develop
```

#### 2.4.2 Bug 修复分支 (bugfix/*)

```
创建流程:
develop ──→ bugfix/<desc> ──→ develop

操作步骤:
1. 从 develop 创建分支
   git checkout develop
   git checkout -b bugfix/fix-description

2. 修复并测试
   # ... 修复代码 ...
   git add .
   git commit -m "fix(scope): resolve issue"

3. 创建 PR 合并到 develop
```

#### 2.4.3 热修复分支 (hotfix/*)

```
创建流程:
main ──→ hotfix/<ver> ──→ main + develop

操作步骤:
1. 从 main 创建分支
   git checkout main
   git checkout -b hotfix/v1.2.1

2. 紧急修复
   # ... 紧急修复代码 ...
   git add .
   git commit -m "hotfix: critical fix"

3. 合并到 main（紧急发布）
   git checkout main
   git merge hotfix/v1.2.1
   git tag -a v1.2.1 -m "Release v1.2.1"

4. 合并到 develop（同步更改）
   git checkout develop
   git merge hotfix/v1.2.1
```

### 2.5 分支保护规则

#### 2.5.1 受保护分支

| 分支 | 直接推送 | 强制推送 | 合并 PR | 状态检查 | 审批要求 |
|------|---------|---------|---------|----------|----------|
| `main` | 🔴 ❌ | 🔴 ❌ | 🔴 ✅ 必须 | 🔴 ✅ 必须 | 1 人 |
| `develop` | 🔴 ❌ | 🔴 ❌ | 🔴 ✅ 必须 | 🔴 ✅ 必须 | 1 人 |

#### 2.5.2 保护规则配置

在 GitHub 仓库设置中配置：

**main 分支**：
- [x] 保护分支
- [x] 要求 pull request 合并
- [x] 要求审批：1 人
- [x] 要求状态检查通过：CI、PR Validation
- [x] 禁止管理员绕过
- [x] 禁止强制推送

**develop 分支**：
- [x] 保护分支
- [x] 要求 pull request 合并
- [x] 要求审批：1 人
- [x] 要求状态检查通过：CI、PR Validation
- [x] 禁止管理员绕过
- [x] 禁止强制推送

## 三、提交规范

> 🔴 [M] **强制执行** - 所有提交必须遵循

### 3.1 提交消息格式

遵循 **Conventional Commits** 标准：

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 3.2 类型 (Type)

| 类型 | 描述 | 语义版本影响 |
|------|------|-------------|
| `feat` | 新功能 | minor |
| `fix` | Bug 修复 | patch |
| `docs` | 文档更新 | - |
| `style` | 代码格式 | - |
| `refactor` | 重构 | - |
| `perf` | 性能优化 | - |
| `test` | 测试相关 | - |
| `chore` | 构建或辅助工具 | - |
| `hotfix` | 紧急热修复 | patch |
| `release` | 版本发布 | - |

### 3.3 范围 (Scope)

范围可以是：

- 模块名称：`auth`、`api`、`ui`、`db`
- 项目名称：`devstation`、`ops-platform`、`scheduler`
- 文件夹名称：`products/devstation/backend`

### 3.4 示例

```bash
# 新功能
feat(auth): add OAuth2 login support

# Bug 修复
fix(api): resolve timeout issue in high load

# 文档更新
docs: update README with new setup instructions

# 热修复
hotfix: security patch for authentication bypass

# 重构
refactor(database): optimize query performance

# 版本发布
release: prepare v1.0.0
```

### 3.5 提交消息检查

CI/CD 流水线会自动检查提交消息格式：

```yaml
# pr-validation.yml 中的检查
- name: Validate PR title
  uses: actions/github-script@v7
  with:
    script: |
      const pattern = /^(feat|fix|docs|style|refactor|perf|test|chore|hotfix|release)(\(.+\))?: .+/;
      if (!pattern.test(title)) {
        throw new Error('Invalid commit message format');
      }
```

## 四、代码质量规范

> 🔴 [M] **强制执行** - 所有代码必须通过质量检查

### 4.1 代码格式

| 语言 | 格式化工具 | 配置文件 |
|------|-----------|----------|
| Go | gofmt / gofumpt | 无 |
| TypeScript | Prettier | .prettierrc |
| Python | Black | pyproject.toml |
| Markdown | Prettier | .prettierrc |

### 4.2 Lint 检查

| 语言 | Lint 工具 | 配置文件 |
|------|----------|----------|
| Go | golangci-lint | .golangci.yml |
| TypeScript | ESLint | .eslintrc.js |
| Python | flake8 / pylint | setup.cfg |

### 4.3 测试要求

| 类型 | 覆盖率要求 | 说明 |
|------|-----------|------|
| 单元测试 | > 70% | 核心业务逻辑 |
| 集成测试 | > 50% | API 和服务 |
| E2E 测试 | 关键流程 | 前端关键路径 |

### 4.4 代码审查

- 所有合并到 `develop` 和 `main` 的 PR 必须经过审查
- 至少 1 人审批
- 审批者应是团队成员或 Maintainer

## 五、版本管理规范

> 🟡 [R] **推荐执行** - 建议遵循

### 5.1 版本号规范

采用 **语义化版本 (Semantic Versioning)**：

```
<major>.<minor>.<patch>

示例：v1.2.3
```

| 组件 | 变化 | 示例 |
|------|------|------|
| major | 不兼容的 API 变更 | v1 → v2 |
| minor | 向后兼容的新功能 | v1.2 → v1.3 |
| patch | 向后兼容的 bug 修复 | v1.2.3 → v1.2.4 |

### 5.2 版本标签

```bash
# 创建发布标签
git tag -a v1.0.0 -m "Release v1.0.0"

# 推送标签
git push origin v1.0.0

# 预发布标签
git tag -a v1.0.0-rc.1 -m "Release candidate 1"
```

### 5.3 Changelog

每个发布必须更新 CHANGELOG.md：

```markdown
# Changelog

## [v1.0.0] - 2026-02-01

### Added
- Feature A
- Feature B

### Fixed
- Bug C
- Bug D

### Changed
- API update
```

## 六、CI/CD 流水线规范

> 🔴 [M] **强制执行** - 所有项目必须通过 CI 检查

### 6.1 流水线结构

```
┌─────────────────────────────────────────────────────────────────┐
│                        CI 流水线流程                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Push/PR ──→ Lint ──→ Test ──→ Build ──→ Security ──→ Merge   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 6.2 必需工作流

每个子项目必须包含以下 GitHub Actions 工作流：

| 工作流 | 文件 | 触发条件 | 说明 |
|--------|------|----------|------|
| CI | `ci.yml` | push/PR 到 main, develop | 代码检查、测试 |
| PR Validation | `pr-validation.yml` | PR 到 main, develop | PR 检查 |

### 6.3 质量门禁

| 检查项 | 失败处理 |
|--------|----------|
| Lint 错误 | ❌ 阻止合并 |
| 测试失败 | ❌ 阻止合并 |
| 覆盖率不足 | ⚠️ 警告，建议修复 |
| 安全漏洞 | ❌ 阻止合并 |
| 提交格式错误 | ❌ 阻止合并 |

## 八、违规处理

### 8.1 违规检测

CI/CD 流水线会自动检测以下违规：

- [x] 分支命名不符合规范
- [x] 提交消息格式错误
- [x] 代码检查失败
- [x] 测试失败
- [x] 安全漏洞
- [x] 缺少必需的审批

### 8.2 违规处理

| 违规类型 | 处理方式 |
|----------|----------|
| 分支命名违规 | ❌ PR 被阻止 |
| 提交格式违规 | ❌ CI 失败 |
| 测试失败 | ❌ PR 被阻止 |
| 安全漏洞 | ❌ PR 被阻止 |
| 缺少审批 | ❌ PR 被阻止 |

### 8.3 申诉流程

如果认为检测结果有误：

1. 在 PR 中添加评论说明
2. 联系项目 Maintainer
3. Maintainer 审核后决定是否放行
